## 코드 수정 및 파일 수락 규칙

# 단일 작업 후 3중 자체 검증 및 코드 품질 보증 규칙

에이전트는 코드나 설정을 수정한 후, 단지 "수정 완료"로 끝내거나 사용자의 확인에 의존해서는 안 된다. 
사용자를 QA 테스터로 취급하는 미완성 보고를 엄격히 금지하며, 에이전트 스스로 100% 확신이 드는 완벽한 결과물만을 보고해야 한다.

코드나 설정 변경이 발생한 경우, 반드시 다음 **3중 검증 절차**를 스스로 수행하고 그 결과를 확인한 후 사용자에게 보고한다.

1. **파일 저장 검증**: 수정 사항이 대상 파일에 정확한 변수명과 문법으로 올바르게 저장되었는지 확인한다.
2. **UI 렌더링 검증**: UI 요소(Streamlit 등)가 수정된 경우, 프론트엔드 상태(Session State 등)와 변수가 제대로 매핑되어 화면상에 의도한 값이 정확히 뜨는지, 양방향 동기화가 제대로 이루어지는지 확인한다.
3. **백엔드 로그 검증**: 봇 엔진이나 백엔드 로직이 수정된 설정을 물고 돌아갈 때, 크래시(Crash)나 에러 로그(참조 오류 등) 없이 정상적으로 반영되어 동작하는지 터미널 로그를 통해 끝까지 추적해서 확인한다.

# [최우선 운영 원칙] 봇 시스템 자동 감시·자가진단·자가복구 의무

이 시스템은 사용자가 문제를 발견해서 지시할 때까지 기다리는 방식으로 운영해서는 안 된다.

사용자가 하루 또는 이틀에 한 번씩 직접 확인하고,
“왜 무포지션이지?”
“포지션이 왜 안 잡혔지?”
“장부 관리가 잘못된 것 같은데?”
“문제가 있는지 확인하고 조치해라.”
라고 반복해서 지시해야만 문제를 발견하는 구조는 **절대 허용하지 않는다.**

시스템은 항상 스스로 자신의 정상 작동 여부를 감시하고 이상을 조기에 발견하여 원인을 분석하고 필요한 조치를 수행해야 한다.

---

## 1. 포지션 상태 자동 감시

각 봇에 대해 지속적으로 다음 사항을 자동 점검한다.

* 현재 LONG / SHORT / 무포지션 상태
* 전략상 포지션을 보유해야 하는 상황인지 여부
* 진입 신호가 발생했는데 주문이 실행되지 않았는지
* 주문은 실행됐지만 포지션 반영이 되지 않았는지
* 포지션은 존재하지만 내부 장부에는 기록되지 않았는지
* 내부 장부에는 포지션이 있다고 되어 있지만 실제 거래소에는 없는지
* 주문 미체결, 부분 체결, 주문 취소, 주문 실패 여부
* TP/SL 주문이 정상적으로 존재하는지
* 포지션과 TP/SL의 수량 및 방향이 일치하는지

단순히 “현재 무포지션이다”라는 사실만 확인해서는 안 된다.

**무포지션이 정상적인 상태인지, 비정상적인 상태인지 반드시 판단해야 한다.**

비정상적인 무포지션이 발견되면:

1. 원인을 자동 분석한다.
2. 관련 로그와 주문 상태를 확인한다.
3. 거래소 실제 상태와 내부 상태를 비교한다.
4. 안전하게 복구할 수 있는 경우 자동 복구한다.
5. 자동 복구가 위험하거나 불가능한 경우 즉시 명확하게 경고한다.
6. 문제와 원인, 조치 결과를 기록한다.

---

## 2. 거래 장부(Trade Ledger) 자동 검증

장부 관리는 사람이 수시로 검사해야 하는 항목이 아니다.

시스템이 스스로 지속적으로 검증해야 한다.

다음 항목을 서로 대조한다.

**거래소 실제 데이터 ↔ 주문 기록 ↔ 포지션 기록 ↔ 거래 장부 ↔ 손익 기록 ↔ 잔고 기록**

다음과 같은 불일치를 자동으로 탐지한다.

* 실제 체결 수량과 장부 수량 불일치
* 실제 진입 가격과 장부 진입 가격 불일치
* 실제 청산 가격과 장부 청산 가격 불일치
* LONG/SHORT 방향 불일치
* 거래 횟수 불일치
* 손익 계산 불일치
* 수수료 반영 오류
* 레버리지 계산 오류
* 실현손익과 미실현손익 혼동
* 포지션 종료 후 장부가 종료 상태로 변경되지 않는 문제
* 거래는 발생했는데 장부에 누락되는 문제
* 장부에는 거래가 있는데 거래소 실제 체결 내역이 없는 문제
* 중복 거래 기록
* 중복 청산 기록
* 잘못된 잔고 계산
* 봇 재시작 후 상태 복원 오류

**장부와 거래소의 실제 상태가 다르면 반드시 이상 상태로 판단하고 원인을 추적한다.**

---

## 3. 자동 Health Check 시스템

모든 봇은 상시적으로 자신의 건강 상태를 점검해야 한다.

최소한 다음 항목을 자동 점검한다.

* API 연결 상태
* 거래소 연결 상태
* 데이터 수신 상태
* 캔들 데이터 정상 여부
* 전략 엔진 정상 작동 여부
* 주문 엔진 정상 작동 여부
* 포지션 관리 엔진 정상 작동 여부
* TP/SL 관리 정상 여부
* 장부 기록 정상 여부
* 잔고 계산 정상 여부
* 봇 프로세스 정상 실행 여부
* 예외 발생 여부
* 최근 거래 이후 상태 정상 여부

단순히 프로그램이 실행되고 있다는 이유만으로 정상이라고 판단하지 않는다.

**프로세스가 살아 있지만 실제 거래 기능이 멈춰 있는 상태도 장애로 판단해야 한다.**

---

## 4. 이상 징후 자동 탐지

사용자가 직접 발견하기 전에 시스템이 먼저 발견해야 한다.

예:

* 일정 시간 이상 예상되는 포지션이 없음
* 진입 신호가 반복적으로 발생하지만 주문이 체결되지 않음
* 주문 요청 후 거래소 응답이 없음
* 포지션과 주문 상태가 서로 다름
* 장부와 거래소 데이터가 다름
* 손익 계산이 비정상적으로 변화함
* 봇이 반복적으로 동일한 오류를 발생시킴
* 특정 봇만 다른 봇과 비정상적인 상태를 보임
* 포지션 종료 후 잔여 주문이 남아 있음
* TP/SL이 사라졌는데 포지션은 살아 있음
* 포지션은 사라졌는데 내부 상태는 계속 보유 중으로 표시됨

이러한 상황을 **사후적으로 발견하는 것이 아니라 실시간 또는 주기적으로 조기에 발견**해야 한다.

---

## 5. 자동 원인 분석

이상 상태가 발생하면 단순히

“오류 발생”
“무포지션”
“장부 오류”

라고 보고해서는 안 된다.

반드시 가능한 원인을 단계적으로 추적한다.

예:

**신호 발생 → 주문 요청 → 거래소 응답 → 체결 → 포지션 생성 → TP/SL 생성 → 장부 기록**

이 전체 흐름 중 어느 단계에서 문제가 발생했는지를 찾아야 한다.

원인을 확인하지 못한 경우에는 추측해서 원인을 만들어내지 말고,

**“원인 확인 불가 — 추가 검증 필요”**

라고 명확하게 표시한다.

---

## 6. 자동 복구 원칙

문제가 발견되면 가능한 경우 시스템이 스스로 복구한다.

단, 자동 복구가 새로운 손실이나 잘못된 포지션을 만들 가능성이 있는 경우에는 임의로 거래하지 않는다.

특히 다음 사항은 매우 신중하게 처리한다.

* 잘못된 포지션 강제 생성
* 임의의 LONG/SHORT 진입
* 중복 주문
* 중복 청산
* 잘못된 TP/SL 생성
* 장부를 임의로 수정하여 실제 거래 기록을 왜곡하는 행위

**안전하지 않은 자동 복구는 하지 않는다.**

필요하면 거래를 일시 정지하고 사용자에게 정확한 원인과 상태를 보고한다.

---

## 7. 사용자에게 문제 발견을 의존하지 않는다

다음과 같은 운영 방식은 실패로 간주한다.

> 사용자가 문제 발견
> → ChatGPT에게 점검 지시
> → 문제 발견
> → 수정
> → 며칠 후 또 사용자가 문제 발견
> → 다시 점검

이러한 반복 구조를 제거하는 것이 시스템 설계의 핵심 목표다.

목표는 다음과 같다.

> **시스템이 스스로 감시한다.
> → 이상을 스스로 발견한다.
> → 원인을 스스로 추적한다.
> → 안전한 경우 스스로 복구한다.
> → 결과를 기록한다.
> → 동일 문제가 재발하지 않도록 원인을 관리한다.**

---

## 8. 동일 문제의 반복 발생 방지

같은 유형의 문제가 반복해서 발생하면 단순히 매번 땜질식으로 수정하지 않는다.

반드시 다음을 수행한다.

1. 과거 동일 오류를 검색한다.
2. 최초 발생 원인을 확인한다.
3. 왜 기존 수정으로 재발을 막지 못했는지 분석한다.
4. 구조적인 해결책을 찾는다.
5. 자동 감시 항목에 해당 문제를 추가한다.
6. 재발 방지 검증을 수행한다.
7. 테스트 결과를 기록한다.

**한 번 수정한 문제가 같은 원인으로 다시 발생하면 해당 수정은 충분하지 않은 것으로 판단한다.**

---

## 9. 수정 후 반드시 검증

코드를 수정했다고 해서 “수정 완료”라고 보고해서는 안 된다.

반드시 다음을 확인한다.

**수정 → 실행 → 테스트 → 실제 상태 확인 → 기존 기능 영향 확인 → 로그 확인**

검증하지 못한 경우에는 절대로

“완료”
“해결”
“정상 작동”

이라고 단정하지 않는다.

검증 결과를 근거로 다음 중 하나로 보고한다.

* 정상 확인
* 부분적으로 정상
* 추가 검증 필요
* 해결하지 못함
* 원인 확인 불가

---

## 10. 다른 봇의 전략을 절대로 훼손하지 않는다

특정 봇의 문제를 수정할 때 다른 봇의 전략, 진입 조건, 청산 조건, 리스크 관리 등에 영향을 주어서는 안 된다.

공통 모듈을 수정해야 하는 경우에는:

1. 영향을 받는 모든 봇을 식별하고
2. 변경 전후 동작을 비교하며
3. 기존 전략이 변경되지 않았음을 검증하고
4. 회귀 테스트를 수행한다.

**한 봇을 고치기 위해 다른 봇의 전략을 망가뜨리는 것은 절대 허용하지 않는다.**

# 최종 운영 철학

이 시스템은

**“사용자가 관리하는 봇”이 아니라
“스스로 자신의 상태를 관리하고 감시하는 봇”**

을 목표로 한다.

사용자가 하루에 한 번 또는 이틀에 한 번씩 직접

* 무포지션 여부 확인
* 포지션 이상 여부 확인
* 장부 확인
* 손익 확인
* 주문 확인
* 오류 확인
* 문제 발생 시 수동 조치

를 반복해야 한다면 시스템 설계가 충분하지 않은 것이다.

**사용자가 문제를 발견하기 전에 시스템이 먼저 문제를 발견해야 한다.**

그리고 문제가 발견되면

**탐지 → 원인 분석 → 안전한 자동 복구 → 장부 정합성 확인 → 재발 방지 → 결과 기록**

의 순서로 자동 처리한다.

단, 확인하지 않은 사실을 정상이라고 보고하지 않는다.

**검증되지 않은 것은 정상으로 간주하지 않는다.**

**추측하지 않는다.**

**문제가 없다는 것을 확인하지 못했으면 “정상”이라고 보고하지 않는다.**

**항상 실제 거래소 상태를 최종 기준으로 삼아 내부 상태·포지션·주문·장부가 일치하는지 검증한다.**
